## Word 操作流程

1. 在桌面版 Word 打开合成稿副本。从功能区打开“论文格式检查”窗格，确认标题、分析按钮和中文界面正常。
2. 点击“分析当前文档”。等待 Word 打开新的 `-格式标注-` 文档；不要通过 CLI 预先生成标注稿。
3. 确认错误示例得到黄色高亮，Word 原生批注分别对应宋体、Times New Roman 和 12pt。同一规则、目标格式和处理级别合并为一个问题及一条批注；核对各处高亮，并用“上一处/下一处”逐处定位，不能将 run 数等同于问题数。每条批注只显示“要求参考来源、规则、期望值、实际值”四项。侧栏问题列表默认折叠，侧栏保留分析、问题/位置导航、修复此项和预览并修复全部等操作。
4. **纯鼠标悬停单独测试**：不点击、不拖选正文。将鼠标停在每处黄色高亮至少一秒，记录 Word 批注区是否突出对应批注，以及侧栏当前项是否同步。每条都单独记录；点击/选中后的结果不能记作悬停通过。
5. **反向定位单独测试**：点击 Word 原生批注卡片，确认光标/视图定位到对应正文范围。再分别测试点击/选中正文高亮的回退行为。确认侧栏没有展开另一套重复的完整批注列表；需要浏览更多问题时才手动展开。
6. 使用“上一项/下一项”选择一个可自动修复的问题，执行“修复此项”，在预览中核对范围和值后确认。确认 Word 没有关闭/重开文档或生成新结果文档；重新分析，确认只改了所选属性、相关批注已刷新、其余问题仍能定位。用一次 Ctrl+Z 撤销该修复，再用 Ctrl+Y 恢复，确认格式与批注一起变化。
7. 对同一合成稿打开“预览并修复全部”。先取消一次，确认文档无变化；再确认批量修复，检查剩余诊断和批注。确认批量操作可以整体 Ctrl+Z 撤销、再 Ctrl+Y 恢复；做完单项和批量操作后再 Ctrl+S 保存工作副本，并验证输入原稿哈希不变。
8. 打开 `clean_sample.docx` 副本并分析，确认显示 0 条问题，不生成问题批注或高亮。保存并重开此工作副本，再分析一次，确认仍在同一文档中更新，没有再次生成副本。
9. 在一份合成稿中做一个未保存的格式修改后直接分析，检查结果是否反映屏幕上的当前值；记录源文件哈希不变。另开第二个 Word 文档窗口重复分析与定位，确认两窗的侧栏、当前问题和批注不会串位。
10. 对已标注副本重复分析，确认工具批注被刷新而非重复累积；用户手工添加的普通批注保留。

## Word 对象模型回归检查（Issue #85）

先编译 VSTO 插件和协议宿主，再从仓库根目录运行以下命令；需要 Windows PowerShell 5.1、Word 桌面版和 Word PIA。脚本只扩展仓库合成夹具，测试产物放在被忽略的 `TestResults/`；它只关闭自己打开的测试文档。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Test-WordInPlaceRepair.ps1 -Configuration Debug
```

2026-10-22 宿主核查发现，本机 `Word.Application` 的 COM 注册指向 WPS。此前脚本输出不能作为 Microsoft Word 验收证据，原“Word 检查通过”记录已撤回。本次分组、单项/批量修复、撤销/恢复及保存重开仍需在 Microsoft Word 中重测。

脚本现在会在激活前核对 `Word.Application` 注册的程序必须为 Microsoft `WINWORD.EXE`，激活后再次核对宿主路径；指向 WPS 等其他程序时直接失败，不开始验收。只有 Microsoft Word 宿主的通过结果才可记录为对象模型回归通过；功能区按钮、预览取消、位置导航按钮及纯悬停仍按上表逐项验收。
