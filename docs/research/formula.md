# 公式排版：检查项、依据与取舍

对应 Issue #114。第一档（只查不改）已实现，命令 `analyze-formula`。本文记录每条检查的出处、为什么这么判、以及明确不做什么，避免以后重复讨论。

## 为什么公式要单独一个入口

纯 OMML 的公式段里没有 `<w:r>`，也没有 `<w:t>`——公式内容全在 `<m:t>` 里。任何「遍历段落取文字 → 判断格式」的写法都会把这类段落当成空段落跳过，于是公式一段都查不到，报告却是 0 条问题。这种假阴性比崩溃更难发现：用户看到「已检查的公式项均符合」，实际什么都没查。

所以实现的入口是反向的：先从 `m:oMathPara` / `m:oMath` 找到公式，再由公式向上找所在段落。`FormulaAnalyzerTests.StandaloneFormulaWithoutWordRunsIsStillDetected` 就是这条的守卫，改实现时它必须保持通过。

## 独立成段与行内的判定

判据是「段落里不属于公式的正文文字还剩不剩」，而不是「有没有 `m:oMathPara`」：

- Word 2016 写 `<m:oMathPara><m:oMath>`，WPS 有时只写 `<m:oMath>`。只认前者会漏掉后者。
- 反过来，一个段落里既有正文文字又有公式时，公式是句子的一部分，套用「居中 / 右对齐」没有意义，必须归为行内。

行内公式只计数，不参与任何排版检查。

表格排版（公式一格、式号一格）单独作为一种布局：位置由列宽决定，不按段落对齐判断居中，右对齐改看式号所在单元格的段落对齐。

## 检查项与出处

| 编号 | 检查项 | 依据 | 是否规范明文 |
| --- | --- | --- | --- |
| F1 | 独立公式居中 | 无条款 | 否，排版惯例 |
| F2 | 式号右对齐 | R13（4.7 表4.6） | 是 |
| F3 | 式号加圆括号、Times New Roman 10.5 磅 | R13（4.7 表4.6） | 是 |
| F4 | 公式内字体 Cambria Math | 无条款 | 否，Word 默认 |
| F5 | 公式段段前段后 0 磅 | R11（4.7 表4.6） | 是 |

报告把两类分开列：**不符合规范** 与 **排版惯例提示**。惯例项不算进规范符合性，理由很实际——`general.yaml` 里查不到条款就不给它编一个。拿惯例当校规去要求用户，用户拿着规范原文来对，对不上，整份报告的信任就没了。

### 几处容易判错的地方

- **行距不查。** R11 自带豁免：「段落中有数学表达式时，可根据表达需要设置该段的行距」。既然规范允许按表达需要调，就不该报。段前段后没有这个豁免，仍按 0 磅查。
- **只查显式设置。** run 上没写字体字号，是继承样式，凭空断言「不是 Times New Roman」会造出一堆误报，而样式继承本身归 `analyze-styles` 管。
- **裸数字式号要认。** 式号写成 `3`（没有圆括号）时，如果只按 `(3)` 的正则去找，就认不到式号，于是当成「无式号」静静放过，「未加圆括号」这条永远报不出来。所以另有一条裸数字兜底识别。
- **制表位要看位置。** 有右制表位不等于对齐了版心右缘，位置可能偏左。容差取 500 twips（约 0.88cm），超出就报位置不对。版心宽 = 页宽 − 左右页边距，从 `sectPr` 读。

## Word 实际写出来的结构和手写样本不一样

2026-11-09 在 Word 16.0 上用 COM 生成真实公式文档后解包确认，Word 的输出有三处和「照直觉手写」的 OMML 不同：

```xml
<w:pPr><w:tabs><w:tab w:val="right" w:pos="8278"/></w:tabs><w:jc w:val="center"/></w:pPr>
<m:oMathPara><m:oMath>
  <m:r><w:rPr><w:rFonts w:ascii="Cambria Math" …/><w:sz w:val="21"/></w:rPr><m:t>E=mc^2</m:t></m:r>
  <m:r><w:rPr><w:rFonts w:ascii="Cambria Math" …/><w:sz w:val="21"/></w:rPr><w:tab/><m:t>(1)</m:t></m:r>
</m:oMath></m:oMathPara>
```

1. **式号在公式对象内部**，是 `m:t` 而不是 `w:t`，靠 `m:r` 里的 `w:tab` 推到段落右制表位。
2. **没有 `m:oMathParaPr`**，居中靠 `w:pPr/jc`。
3. **式号的字体是 `Cambria Math`**，因为它在公式里，字体由公式引擎决定。

第一版实现只读 `w:t`，于是在真实文档上「带式号 0 个」——式号被当成公式文本的一部分，F2 和 F3 全部不检查，报告还显示「已检查的公式项均符合」。这是本次实机验证抓到的真问题，不是推测：手写样本里式号是我自己放在 `w:t` 里的，所以样本一直绿。

修正后式号有两条识别路径：公式内有 `w:tab` 时取制表符之后的 `m:t`；没有制表符时取末段 `m:t`，但**只认带圆括号的**——公式末尾经常是 `2`、`n` 这种单字符，按裸数字认会把公式内容当式号，凭空报一条「式号未加圆括号」。

第 3 点带来一个口径取舍：**式号在公式对象里时不查字体，只查字号**。字体是公式引擎给的，用户没有实际选择权，照 R13 报「应为 Times New Roman」等于让所有用 Word 公式编辑器的人都背着一条改不掉的错。字号（`w:sz`）仍然是用户能改、规范也明确要求 10.5 磅的，照查。这个取舍的代价是：用户若在公式里手动把式号设成宋体，这里查不出来。

## 明确不做

**不做 LaTeX → OMML 语义转换。** `AfishInLake/WordFormat` 的 `latex2mathml` + `mathml2omml` 管线技术上可行，但我们没有把 OMML 渲染回去做验证的能力，转错了没人能发现。用户手上有 Word 公式编辑器或 MathType，公式写不对的痛感远低于格式不统一。等第二档稳定、有回读能力了再单独立项。

**不做公式编号自动重排。** 跨章节编号牵动全文顺序，改错一次整篇编号全乱，收益不抵风险。

## 未覆盖

- 公式编号的连续性与重复：需要跨章节顺序判断，属编号重排范畴。
- 两列表格排版下公式在单元格内是否居中：位置由列宽决定，XML 层面判不准。
- 公式渲染是否正确：`m:t` 只用于报告预览，不参与判断。
- WPS 存出的公式常缺 `rPr`，此时按「继承 Word 默认」处理，不报字体问题——这一条是保守选择，可能漏掉真实的字体偏差。

## 与参考实现的对照

`AfishInLake/WordFormat`（Apache-2.0）的 `src/wordformat/rules/math.py` 处理了「纯 OMML 段没有 `w:r` 导致段落级检查跳过」这个坑，本实现在入口设计上采用了同样的思路（从公式反向找段落），但代码是独立编写的，未复制其实现。它的 `math/omml.py` 里 `m:r` 缺 `w:rPr` 的兜底写法也在 F4 的「缺省不报」里体现。
